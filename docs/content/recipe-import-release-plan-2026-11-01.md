## 一、核心结论

建议采用「首批 50 道经典中餐 → 扩展至 200 道实用食谱 → 建立持续更新的中餐食谱库」的三阶段策略。

但 CNrecipe 不应该简单地把网上最有名的 50 道菜复制进数据库。

CNrecipe 的定位是实用型中餐烹饪工具，因此首批食谱需要同时满足三个目标：

1. 经典性：具有一定的文化代表性、地域认知度和烹饪价值。
2. 实用性：普通家庭能够获取食材、完成制作，并愿意反复使用。
3. 产品适配性：能够支持按食材搜索、My Kitchen 库存匹配、购物清单及逐步烹饪模式。

### 研究依据

2018 年，中国烹饪协会正式发布《中国菜——全国省籍地域经典名菜、主题名宴名录》，覆盖 34 个地域菜系、340 道地域经典名菜及 273 席主题名宴。它可以为 CNrecipe 建立有出处的候选菜品库。

不过，经典名菜不等于最适合家庭烹饪的菜。例如佛跳墙、北京烤鸭具有很强的代表性，却不适合优先承担新用户的日常做饭需求。

## 二、首批 50 道食谱的筛选标准

建议采用两层审核：先排除版权、安全和可复现性不合格的菜谱，再对其余候选菜品进行评分。

### 2.1 选品评分模型

| 评价维度    | 权重   | 核心判定           |
| ------- | ---- | -------------- |
| 经典代表性   | 25%  | 名菜名录、地域传统与文化认知 |
| 日常烹饪需求  | 20%  | 家庭使用频率与复做价值    |
| 食材可获得性  | 15%  | 普通超市、菜市场是否容易买到 |
| 烹饪可复现性  | 15%  | 步骤能否标准化，结果是否稳定 |
| 食材复用价值  | 10%  | 能否与其他食谱共享常用食材  |
| 品类多样性   | 10%  | 对菜系、食材、技法的补充价值 |
| 内容制作可行性 | 5%   | 原创图文、审核与制作成本   |
| 合计      | 100% |                |

建议将 75 分设为常规入选线，65–74 分进入候补库。对具有重要文化代表性、但家庭制作门槛较高的菜品，可以设置少量特别入选名额。

版权不清、存在不可控食品安全风险、无法形成可靠步骤的菜谱不得因评分高而发布。

## 四、食谱内容生产与导入规范

这部分决定 CNrecipe 最终是普通图文菜谱库，还是可以长期扩展的烹饪工具。

### 4.1 数据来源策略

| 获取方法            | 适用情况         | 建议          |
| --------------- | ------------ | ----------- |
| 官方行业名录、传统烹饪资料   | 确定经典菜品、地域与技法 | 用于研究与选品     |
| 自主编辑与实做验证       | 生成完整食谱正文与步骤  | 首批主要方法      |
| 有授权的第三方食谱数据/API | 快速扩充内容规模     | 后续评估成本和许可   |
| 用户投稿或厨师合作       | 增加地方风味与版本    | 200 道之后逐步引入 |
| 未经许可的网页批量抓取     | 直接复制图文、照片    | 不采用         |

中国现行著作权法保护符合条件的文字、摄影等作品，因此不能把菜品名称可供参考，误认为其他平台的图文食谱也可以自由复制。

对图片，可以使用原创拍摄、明确商业授权素材，或符合许可条件的内容；例如 CC BY 4.0 允许商业使用，但有署名、许可链接和修改说明等要求。

### 4.2 每道食谱的标准数据契约

建议以内部结构化数据作为唯一正式来源，支持 JSON、CSV 草稿导入，最终通过管理后台审核发布。

| 数据模块    | 必填字段                           |
| ------- | ------------------------------ |
| 身份信息    | Recipe ID、标准菜名、别名、内容版本         |
| 分类标签    | 地域、菜系、菜品分类、烹饪技法、难度             |
| 时间份量    | 备料时间、烹饪时间、总时间、人数               |
| 食材清单    | Ingredient ID、名称、精确数量、单位、必需/可选 |
| 烹饪步骤    | 顺序、动作、火候、用时、关键判断点              |
| 设备工具    | 炒锅、蒸锅、电饭煲等                     |
| 安全与饮食信息 | 食物过敏原、特殊处理及安全提示                |
| 图像资源    | 封面、可选步骤图、授权来源                  |
| 审核记录    | 来源依据、编辑人、验证结果、审核状态             |
| 发布信息    | 发布状态、时间、修订版本、撤回记录              |

国际通用的 Schema.org `Recipe` 结构包含食材、步骤、份量、分类、准备时间、烹饪时间等字段，可作为兼容性参考；CNrecipe 还需要额外建立食材标准化 ID、库存匹配与内容审核字段。

### 4.3 一份可执行食谱的质量要求

以西红柿炒鸡蛋为例，不能只写“鸡蛋炒熟后加入番茄，调味即可”。

需要明确食材克数、用量和人数；下锅次序；火力强弱；每一步的持续时间或熟度判断；以及可选调味品是否影响原版风味。

建议把 原创编辑 + 交叉核查 + 实际烹饪验证 作为首批食谱的标准生产方式。对进阶菜，应邀请熟悉该地域做法的人验证关键工艺。

另外，食品安全规范可参考国家市场监督管理总局发布的《餐饮服务食品安全操作规范》，针对生熟分开、充分加热及再加热等场景设计明确提示。

## 五、食谱导入与审核流程

1. 候选入库

   收集菜名、地域、名录依据与相似菜品，形成独立候选库。
2. 筛选与去重

   根据评分、品类比例和可执行性选出 50 道；识别同名异做、别名和地域版本。
3. 编辑结构化食谱

   AI 可以辅助整理字段、检查遗漏、标准化食材名称，但不能凭空确定未经核实的用量、时间或工艺。
4. 烹饪验证与质量审查

   检查味型、用料、步骤、时间、过敏原、食品安全和图片一致性。
5. 预发布环境导入

   进行字段校验、食材 ID 映射、图片有效性检查、重复导入防护及 App 真实流程测试。
6. 正式发布及监控

   使用版本化批次发布。支持单道撤回、批次回滚、问题修订和旧版本留档。

技术执行上建议采用幂等导入：同一菜品的同一版本重复导入不会产生重复记录；只有通过校验的版本才允许进入正式食谱库。

## 六、与 CNrecipe 产品功能的对接

食谱库必须真正驱动已有功能，而不是独立的数据展示页。

| App 功能          | 食谱数据如何参与                      |
| --------------- | ----------------------------- |
| Explore 搜索      | 标准菜名、别名、主食材、菜系和技法检索           |
| Explore Recipes | 按难度、用时、地域、食材和菜品类型筛选           |
| My Ingredients  | 根据库存中的标准 Ingredient ID 找出可做菜谱 |
| 购物清单            | 自动计算所缺的必需食材和数量                |
| 分步烹饪            | 将每条步骤转换为独立可执行的烹饪卡片            |
| Saved           | 收藏具体食谱及其版本                    |
| Cooking History | 记录实际完成的菜品及用户反馈                |

特别建议建立三种 My Kitchen 结果：已有食材可以做、缺少 1–2 种食材、需要采购较多食材。调味料和可替代材料不能直接当作用户已拥有的必需食材。

此前设计的食材时间血量条，还可以支持临期食材优先推荐。但它只能代表依据保存条件估计的剩余期限，不能判定食材一定安全。国家疾控局也明确提醒，冷藏和冷冻不能消除所有食物变质风险。

## 七、首发发布计划

第 1 周

选品

完成候选库与数据规范

整理约 80 道候选、确定 50 道及替补、完成标准字段与审核模板。

第 2–3 周

20 道

优先交付基础家常食谱

完成编辑、原料标准化、烹饪验证，测试搜索、购物清单和烹饪模式。

第 4–5 周

20 道

补齐地域经典菜品

重点验证复杂技法、地方做法和食材替代的准确性。

第 6 周

10 道

完成全部 50 道并进行首发验收

验证全量搜索、页面展示、图片权限、收藏、库存匹配和发布回滚。通过后公开发布。

以上是建议排期，不是已承诺的完成时间。是否能在六周内交付，取决于编辑、试做、视觉资产与审核资源。可以先进行 20 道内部测试，但正式公开首发以 50 道通过验收为目标。

### 发布准入门槛

- 50 道食谱全部具有完整的用料、步骤、份量与时间数据。
- 所有必需食材均已映射标准 Ingredient ID。
- 50 道全部通过内容审核与适当的烹饪验证。
- 100% 图文素材具有明确来源及可用权限。
- 食谱搜索、详情页、备料、烹饪模式与购物清单端到端测试通过。
- 高风险食品安全问题为零，支持撤回和回滚。

## 八、后续扩充与运营计划

建议从 50 道扩大到 200 道后，再考虑更大规模的内容生产。

| 累计规模    | 重点内容            | 目标        |
| ------- | --------------- | --------- |
| 50 道    | 经典家常 + 地域代表菜    | 验证核心烹饪体验  |
| 100 道   | 快手菜、更多常见蔬菜和蛋白质菜 | 增加复做频次    |
| 150 道   | 早餐、主食、汤羹、家庭套餐   | 覆盖更多用餐场景  |
| 200 道   | 地方特色、季节菜和用户高需求菜 | 形成初步实用食谱库 |
| 200 道以后 | 按真实数据决定扩充方向     | 避免为了数量而收录 |

发布后建议先试行每周 5–10 道的节奏。按每周 10 道计算，从 50 道增加到 200 道需要连续 15 周；如果质量审核无法跟上，应优先降低更新数量而不是压缩验证环节。

后续筛选从编辑主导逐步转为用户需求与内容缺口共同驱动，重点观察：搜索无结果的关键词、用户高频库存食材、菜谱开始烹饪率、完成率、收藏率和实际烹饪反馈。

每次发布应包含修订说明与版本记录；有问题的菜谱优先修复，而不是用新增内容掩盖错误。

## 十、我建议优先落实的事项

下一阶段需要先形成两个正式的数据资产：50 道食谱选品总表，以及1 道完整标准食谱样本。

前者确定食谱库的范围、优先级和制作顺序；后者用真实食谱检验所有数据字段是否足以支撑 CNrecipe 的功能。在完整样本通过搜索、库存匹配、购物清单和逐步烹饪验收后，再把同一规范扩展到其他 49 道。

这样可以避免先做完 50 篇图文，最后却发现无法可靠导入 App 的问题。
