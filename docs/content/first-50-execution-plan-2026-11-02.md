## 1. 目标、边界与完成定义

交付 50 道独立菜式的可追溯、结构化、经过实际烹饪验证的正式候选发布包，并完成隔离环境导入与 App 验收。正式发布另需审核具体发布包、目标环境和回退方案后批准。本计划本身不授权生产写入。

六道现有 demo 按菜式和版本逐一核对：与名单重合者沿用稳定 recipe ID、建立新内容版本；非名单项是否继续展示在发布清单中明确，不能把首批数量计算成 56 道。demo 不因已在 App 中展示而免审，也不覆盖原版本。

完成条件：50 道全部通过内容、许可、安全、实做及技术审核；必需字段、必需食材 ID 和素材权利记录完整率均为 100%；核心流程通过；重复导入不产生重复记录；撤回与回退演练有证据。无法实际试做的菜保持待验证，不以 AI 判断代替。

## 3. 分工与状态管理

角色可由同一人兼任，但关键配方交叉核查由另一位审阅者签署。内容负责人负责选品和原创编辑；核查者负责来源、用量与地域版本；试做者记录实际过程；审核者负责食品安全及发布准入；研发负责模型映射、导入与回退；QA负责真实 App 验证；发布负责人批准并执行正式发布。实际人员在启动前填写，未指派不视为已承担。

状态顺序：候选 → 来源已核查 → 编辑完成 → 交叉核查通过 → 实做通过 → 内容批准 → 技术校验通过 → 隔离环境验收通过 → 待发布 → 已发布。驳回转“待修订”，修订涉及用量、工艺或安全时重新实做和审核；已发布问题可转“已撤回”。每次转换保存人员、日期、内容版本和证据链接。

每道台账字段：候选编号、稳定 recipe ID、标准菜名/别名、地域版本、批次、负责人、来源 URL/版次/访问日、来源快照校验值、文字及图片权利依据、编辑版本、实做记录、食材映射、审核结论、阻断原因、替补关系、发布版本。未知项留空并标记待核查，不编造评分和通过记录。

## 5. 数据获取与内容生产工作包

1. **建立来源档案**：核查新方案提及的行业名录及具体条目；地域标签描述所采用版本，不宣称唯一发源地。逐条补原始链接，不使用粘贴的站点图标作为引用。行业名录只支持选品，不自动提供可执行配方或图文权利。
2. **获取参考材料**：优先正式烹饪资料、作者原始内容和可证明许可的资料；保存出处、访问日、版次、适用许可和引用范围。未经许可不批量复制网页正文或照片。多来源用于核查冲突，不能拼接互相矛盾的用量。
3. **原创编辑**：明确人数、食材精确用量及单位、下锅顺序、火力、用时、熟度判断、设备、可选调料和替代边界；保留中英文名称并复核译名。AI 可辅助格式化和查缺，不确定用量/时间进入待核实问题，不补成事实。
4. **图片制作**：优先拍摄试做成品；记录摄影者、授权依据和与版本的对应关系。第三方许可逐项核查商业用途、署名和修改义务。没有可用封面时不得伪装成素材审核完成。
5. **交叉核查**：用料与步骤双向对照，检查漏列水/油/酱汁、原料净重与采购重、调料复合过敏原、设备容量和总时间口径。独立核查者记录问题及修订。
6. **实做验证**：每道至少一次完整实际制作；记录原料规格、实用量、设备、份数、备料/烹饪时间、关键过程与成品照片、失败点和修订。复杂地方菜由熟悉该做法者核查关键工艺。关键修订后重新验证；一次成功不代表所有人数和设备下均已实测。
7. **安全审核**：执行前查询适用的官方安全依据并保存链接/日期；针对冷菜、木耳、禽肉、水产、贝类、剩饭及预处理原料设逐菜检查。时间提示不能替代熟度判断；不在本计划编造统一安全温度或保存期限。存疑项阻断发布。

## 6. 结构化、适配与导入工作包

先完成一份独立的编辑母数据，再转换成现有 App 文档。不得把待审核数据直接覆盖正式种子。

| 母数据 | 当前消费字段/处理 | 样本关口 |
|---|---|---|
| 稳定菜式 ID、内容版本 | id/version；现有重合菜沿用 ID | 收藏及历史仍可定位旧版本 |
| 菜名、英文名、别名、地域、技法 | chineseName/name/category；其余先做适配评估 | 搜索及筛选逐项实测，不仅保存字段 |
| 人数与时间 | baseServings/minutes；另存备料和烹饪时间 | 总时间包含并行工序时明确口径 |
| 原料、精确数量、单位 | ingredientId/metricQuantity/metricUnit/usQuantity/usUnit | 统一转换依据；不直接把重量换体积，个数需记录规格 |
| 必需/可选、调料与替代项 | 现有数据无充分语义证明 | 明确最小适配，测试库存与购物不默认拥有调味料 |
| 步骤、火力、时间、关键判断 | steps.title/instruction/tip/durationSeconds | 计时字段语义先核对消费者，不能把所有步骤总耗时直接当倒计时 |
| 图片、设备、过敏原 | imageKey/bundledImage/equipment/allergens | 图片与食谱同版；过敏原在产品中可见 |
| 来源、许可、审核和实做 | 独立版本化审核档案 | 发布包能反查证据，不要求全部暴露给客户端 |

导入器为待实现任务：提供 validate、dry-run、apply、rollback 四个明确阶段；输出逐条错误和新增/复用/拒绝清单。校验 ID 格式及唯一性、引用存在、版本正整数、数量与时间类型/范围、非空步骤、枚举、图片路径、审核状态及批次数量。

幂等键为 recipe ID + version：同键同内容哈希跳过；同键不同内容拒绝并要求新版本；禁止覆写不可变版本。食材同 ID 不同语义须人工解决，不能静默改名影响库存。批次在事务内先写食材、目录与版本，再切换指针；利用已有可延迟外键，失败整体回滚。保存导入前指针、active、display_order、数据和资源清单及哈希。

隔离验证顺序：母数据校验 → PGlite 导入 → 重复执行 → 中途故障回滚 → 与现有 API 相同路径查询 → 16 组 quotes 核对 → 同批生成离线资源 → 候选 App 测试。测试数据库确认隔离后才写入，不把生产 API 当测试环境。

照片沿用现有版本路径约定 `recipes/{recipeId}/v{version}.jpg`；核查实际桶约束及上传权限后再上传，下载核对哈希。随包图映射单独生成并验证，不假定 imageKey 足以支持首次离线。

## 9. 撤回、回退与交付目录

回退切换旧 current_version/active/display_order，不删除旧版本或改写用户历史。新增菜无旧版时设为停用；食材共享项和版本文件保留，避免破坏引用。验证 API 和刷新后的客户端不再展示撤回版本；已经离线的内容、在做会话及随包内容不能保证立即撤回，发布前明确这一边界和严重问题的通知/更新处置办法。

计划新增的产物（尚未创建）放在 `docs/content/first-50/`：

- selection.md：50 道总表、候补、批次及状态。
- sources/、reviews/、cook-tests/、image-rights/：逐菜依据、审核、试做和授权记录，记录文件与版本对应关系。
- mapping.md：字段、食材ID、单位及客户端适配决定。
- batches/：逐批机器可读数据、manifest、校验哈希、dry-run和apply报告。
- qa/：样本、全量用例执行证据和缺陷复测。
- releases/：批准包、旧指针快照、回退脚本/演练及发布说明。

导入和校验工具按现有项目组织放 scripts，测试沿用现有测试体系；具体文件名在实现时确定。技术验证使用相关后端测试、内容专项测试、资源构建及真实 App 用例；本文件为计划文档，此次不执行构建、导入、上传、试做或发布，也不声称其已通过。
